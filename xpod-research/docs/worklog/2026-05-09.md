## 0. 背景与起因

### 0.1 论文核心 claim

xPod 提出"三元素联合调度"——一个任务到来时,调度器同时为它选择:

- **compute_node**:计算节点(GPU/CPU)
- **data_node**:数据服务节点(数据集所在)
- **algo_node**:算法服务节点(算法镜像所在)

打分函数综合考虑数据传输代价、镜像拉取代价、计算时间、负载均衡等因素,在三层笛卡尔积中选最优三元组。

### 0.2 用户的真实需求(原话)

> "一个任务来了,是 GPU 任务就走有算力的 vm 节点,数据跟算法就走数据跟算法的 vm 节点。"

### 0.3 之前代码的问题

`schedule_one_xpod()` 实际上**没有在做三元素调度**:

- ✅ `compute_node` 维度:有循环选择
- ❌ `data_node` 维度:**直接从 trace CSV 透传**(datagen 用 dataset_id 哈希伪造)
- ❌ `algo_node` 维度:**完全没有概念**

**结论**:这与论文宣称的"xPod 三元素联合调度"严重不符,审稿人会质疑。算法是直接用的数据源,然后给我提示词,我用 AI 工具按照提示词都改完了——但需要从头验证。

#### 2.2 新增独立类 ResourceCacheState

```python
class ResourceCacheState:
    """跟踪每个 data_node 缓存了哪些 dataset,每个 algo_node 缓存了哪些 image。"""
    def __init__(self) -> None:
        self._dataset_on_data_node: Dict[str, Set[str]] = {}
        self._image_on_algo_node: Dict[str, Set[str]] = {}

    def is_dataset_cached_on(self, data_node: str, dataset_id: str) -> bool:
        return dataset_id in self._dataset_on_data_node.get(data_node, set())

    def mark_dataset_cached(self, data_node: str, dataset_id: str) -> None:
        self._dataset_on_data_node.setdefault(data_node, set()).add(dataset_id)

    def is_image_cached_on(self, algo_node: str, image: str) -> bool:
        return image in self._image_on_algo_node.get(algo_node, set())

    def mark_image_cached(self, algo_node: str, image: str) -> None:
        self._image_on_algo_node.setdefault(algo_node, set()).add(image)
```

### 任务 3:schedule_one_xpod() 改成真正的三层笛卡尔积

**文件**:`scheduler/xpod_scheduler.py`

#### 3.1 函数签名改动

- 参数 `cache` 从 `CacheState` 改为 `ResourceCacheState`
- `ScheduleDecision` 增加 `algo_node: str = ""` 字段(默认空字符串,避免 baseline 兼容性问题)

#### 3.2 主流程

```python
def schedule_one_xpod(row, cluster, cache, job_index, alpha=1.0, beta=1.5, gamma=0.8):
    # 第一步:根据 compute_type 锁定 compute 候选集
    compute_type = (row.get("compute_type") or "").upper()
    compute_candidates = cluster.candidates_for_compute_type(compute_type)
    if not compute_candidates:
        return None

    # 第二步:拿 data 和 algo 候选集(空候选退化为 ("",) 占位)
    data_candidates = cluster.all_data_nodes() or ("",)
    algo_candidates = cluster.all_algo_nodes() or ("",)

    # 第三步:取 xPod 需求字段
    dataset_id = row.get("dataset_id") or ""
    dataset_size_bytes = _as_int(row.get("dataset_size_bytes"), 0)
    algorithm_image = row.get("algorithm_image") or ""
    duration_s = _as_float(row.get("duration"), 0.0)
    dominant_amount = _dominant_resource_amount(row)
    p = _p_2dlas(job_index, dominant_amount)

    # 第四步:在 (compute, data, algo) 笛卡尔积中找最优三元组
    best = None
    for c_node in compute_candidates:
        for d_node in data_candidates:
            for a_node in algo_candidates:
                # 数据维度代价
                dataset_cached = bool(dataset_id) and bool(d_node) and \
                    cache.is_dataset_cached_on(d_node, dataset_id)
                bytes_to_load = 0 if dataset_cached else max(0, dataset_size_bytes)
                data_lat_ms, data_bw_mbps = cluster.network_profile(d_node, c_node)
                data_transfer_ms = estimate_transfer_ms(bytes_to_load, data_bw_mbps, data_lat_ms)

                # 算法维度代价(镜像拉取占位 100MB)
                image_cached = bool(algorithm_image) and bool(a_node) and \
                    cache.is_image_cached_on(a_node, algorithm_image)
                image_size_bytes = 0 if image_cached else 100 * 1024 * 1024
                algo_lat_ms, algo_bw_mbps = cluster.network_profile(a_node, c_node)
                algo_transfer_ms = estimate_transfer_ms(image_size_bytes, algo_bw_mbps, algo_lat_ms)

                # 完成时间 = 计算 + 数据传输 + 镜像拉取
                t_compute = duration_s * (max(1e-9, dominant_amount) ** -0.5)
                t_total = t_compute + data_transfer_ms / 1000.0 + algo_transfer_ms / 1000.0

                # 打分:完成时间越小越好,locality 奖励 + 负载均衡惩罚
                data_locality = _locality_penalty_s(bytes_to_load, d_node, c_node, data_bw_mbps)
                score = (alpha * t_total) + (beta * data_locality) - (gamma * p)

                if best is None or score < best[0]:
                    best = (score, c_node, d_node, a_node, {...metrics...})

    # 第五步:更新缓存
    if dataset_id and d_node:
        cache.mark_dataset_cached(d_node, dataset_id)
    if algorithm_image and a_node:
        cache.mark_image_cached(a_node, algorithm_image)

    return ScheduleDecision(
        compute_node=c_node, data_node=d_node, algo_node=a_node,
        bytes_to_load=..., cold_start=..., score=...
    )
```

#### 4.5 真正原因:network_profile() 让两个 data 节点同质化

查 `scheduler/controller/xpodgen/scheduler.py` 第 56 行附近:

```python
def network_profile(self, data_node: str, compute_node: str) -> Tuple[float, float]:
    if not data_node or not compute_node:
        return self.base_latency_ms, self.base_bandwidth_mbps
    if data_node == compute_node:
        return clamp(self.base_latency_ms * 0.25, 0.1, 10.0), \
               clamp(self.base_bandwidth_mbps * 5.0, 100.0, 100000.0)
    if data_node.split("-")[0] == compute_node.split("-")[0]:
        return clamp(self.base_latency_ms * 0.5, 0.1, 10.0), \
               clamp(self.base_bandwidth_mbps * 2.0, 100.0, 100000.0)
    return self.base_latency_ms, self.base_bandwidth_mbps
```

**逻辑分析**:
- `data-node-1` 与 `gpu-node-1` 比前缀:`"data" != "gpu"` → 兜底,用 base 值
- `data-node-2` 与 `gpu-node-1` 比前缀:`"data" != "gpu"` → 兜底,用 base 值

**两个 data 节点对任何 compute 节点的网络代价完全一样**,score 平局,代码里 `if score < best[0]` 严格小于,平局时不更新 → 永远停在循环遍历的第一个,即 `data-node-1`。

#### 4.6 三种解决方案

- **方案 A**:给每个 data 节点固化不同的网络系数(基于节点对 hash 扰动)
- **方案 B**:让缓存机制驱动选择(更符合论文)——同 dataset 反复出现,第一次冷启动后,有缓存的节点 score 最低
- **方案 C**:运行时随机打破平局(简单但论文讲不清)

**用户决策**:方案 B,这才是 xPod 论文要讲的故事——"通过缓存数据局部性优化调度"。

#### 4.7 方案 B 验证前提

得用能体现缓存效果的数据来跑——前 5 条 trace 的 dataset_id 都不同,所以看不出缓存效果(全是冷启动)。需要构造**同一个 dataset_id 反复出现**的负载。

trace 里两条任务的 `submit_time` 间隔可能很大(几百秒到几千秒),`speedup=60` 意思是 wall-clock 加速 60 倍,但即便如此,几千秒的间隔也要等几十秒到几分钟。

**两种修复**:
- `--speedup 100000`:接近瞬时
- `--speedup 0`:跳过 sleep(看 580-581 行,代码会强制成 0,然后 `if args.speedup > 0` 不进 sleep 分支)

## 3. Baseline 调度器选型(完整决策过程)

### 3.1 检查现有 baseline 实现

```bash
$ grep -n "schedule_one_baseline\|def.*baseline" \
    scheduler/xpod_scheduler.py \
    scheduler/controller/xpodgen/scheduler.py 2>/dev/null

scheduler/xpod_scheduler.py:164:def schedule_one_baseline(

$ sed -n '164,210p' scheduler/xpod_scheduler.py
```

完整实现:

```python
def schedule_one_baseline(
    row: Dict[str, str],
    cluster: ClusterConfig,
    cache: ResourceCacheState,
) -> Optional[ScheduleDecision]:
    g = dag.build_dag(row)
    compute_type = (g.compute.compute_type or "").upper()
    candidates = cluster.candidates_for_compute_type(compute_type)
    if not candidates:
        return None
    data_candidates = cluster.all_data_nodes() or ("",)
    algo_candidates = cluster.all_algo_nodes() or ("",)
    xpod_id = g.xpod_id or ""
    seed_material = f"{cluster.seed}|{xpod_id}".encode("utf-8", errors="ignore")
    seed_int = int.from_bytes(hashlib.sha256(seed_material).digest()[:8], "big", signed=False)
    rng = random.Random(seed_int)
    compute_node = rng.choice(list(candidates))
    data_node = rng.choice(list(data_candidates))
    algo_node = rng.choice(list(algo_candidates))

    # 缓存照常更新(模拟现实中数据真的会被加载到选中节点)
    dataset_id = g.data.dataset_id or ""
    dataset_size_bytes = int(g.data.dataset_size_bytes)
    dataset_cached = bool(dataset_id) and bool(data_node) and \
        cache.is_dataset_cached_on(data_node, dataset_id)
    bytes_to_load = 0 if dataset_cached else max(0, dataset_size_bytes)
    cold_start = 0 if dataset_cached else 1
    if dataset_id and data_node:
        cache.mark_dataset_cached(data_node, dataset_id)

    return ScheduleDecision(
        compute_node=compute_node, data_node=data_node, algo_node=algo_node,
        bytes_to_load=int(max(0, bytes_to_load)),
        network_latency_ms=0.0, network_bandwidth_mbps=0.0,
        estimated_transfer_ms=0.0, cold_start=cold_start, score=0.0,
    )
```

**结论**:这是**纯随机调度**——三个候选集都用 `rng.choice`,只有 hash(seed + xpod_id) 让结果可复现。

**这不是原生 k8s 的对比**。

### 3.2 原生 k8s default-scheduler 的真实逻辑

- **Filter 阶段**:NodeAffinity、TaintToleration、资源够不够过滤
- **Score 阶段**:多个打分插件加权
  - LeastRequestedPriority
  - BalancedResourceAllocation
  - ImageLocality(只看节点是否已拉过镜像,不主动调度数据)
  - NodeResourcesFit
- **关键特征**:有打分,但**完全不感知数据局部性**(没有 data_node 概念)、**ImageLocality 只是被动偏好**(不主动调度算法节点)

### 3.3 对比讨论

| 故事 | 当前可讲 | 论文价值 |
|------|---------|---------|
| xPod vs Random | ✓ | 弱(审稿人:"谁不比随机好") |
| xPod vs k8s default | ✗ | 强(论文硬核 claim) |

### 3.4 三选一

- **方案 A**:保持 random baseline,论文里命名 "Random Baseline",诚实写明它等价于 k8s default 在三元素维度上的行为
- **方案 B**:补 LeastRequested 模拟(compute 选 GPU 占用最低,data/algo 仍随机)
- **方案 C**:完整模拟 k8s default(资源跟踪 + 打分插件)

### 3.5 用户决策:方案 A

**理由**:
1. k8s default-scheduler 的核心打分(LeastRequested、BalancedResourceAllocation)只作用于计算资源
2. ImageLocality 插件只做被动偏好,不主动调度数据
3. **在三元素模型(compute/data/algorithm)下,default-scheduler 在 data 与 algorithm 维度上等价于随机选择**
4. 不补假的 k8s default 模拟器,论文里诚实写

3. 跑 27 分钟可接受
