## 二、问题现象

VM 启动后（`kubectl get vmi` 显示 Running），执行：

```bash
virtctl console cpu-node-1
```

连接成功提示出现，但屏幕完全黑屏，按回车无任何反应，无登录提示。

---

## 三、排查过程

### 阶段一：确认 VM 是否真正在运行

**操作：**
```bash
kubectl get vmi cpu-node-1
virtctl guestosinfo cpu-node-1
```

**结果：**
- VMI 状态为 Running，但 **IP 字段为空**
- guestosinfo 报错：`VMI does not have guest agent connected`

**初步判断：** VM 进程在跑，但内部系统没有正常启动，网络和 guest agent 均未初始化。

---

### 阶段二：尝试 VNC 访问

**操作：**
```bash
virtctl vnc cpu-node-1
```

**结果：**
```
Can't open display:
```

宿主机是纯 server 环境，没有图形界面，VNC 客户端无法启动。

**改用 proxy 模式：**
```bash
virtctl vnc cpu-node-1 --proxy-only --address=0.0.0.0 --port=5901
```

在 Mac 上用 `open vnc://192.168.1.100:5901` 连接，VNC 客户端连上后立即断开。

**分析：** VNC 断开说明 VM 内部还未完成初始化，图形输出不稳定。

---

### 阶段三：尝试 SSH 访问

**操作：**
```bash
ssh leo@192.168.1.131
```

**结果：**
```
ssh: connect to host 192.168.1.131 port 22: No route to host
```

**分析：** VM 网络完全不通，cloud-init 的 netplan 配置没有生效，或者系统根本没有启动完成。

---

### 阶段四：查看 virt-launcher 日志

**操作：**
```bash
kubectl get pod -A | grep cpu-node-1
# 找到 pod 在 default namespace
kubectl logs -n default virt-launcher-cpu-node-1-z6mpw -c compute 2>&1 | tail -80
```

**关键发现：**
- VM 正常通过 QEMU/KVM 启动
- serial 设备已配置（`-chardev socket,id=charserial0`）
- QEMU 进程正常运行（找到 PID）
- 但串口日志文件完全为空

**结论：** QEMU 层面串口设备存在，但 VM 内部没有任何输出写入串口。

---

### 阶段五：检查镜像格式（发现根本原因）

**操作：**
```bash
ls -lh /opt/k8s-workspace/images/cpu-node-1.qcow2
file /opt/k8s-workspace/images/cpu-node-1.qcow2
qemu-img info /opt/k8s-workspace/images/cpu-node-1.qcow2
```

**结果：**
```
661M Apr 20 06:40 cpu-node-1.qcow2
QEMU QCOW Image (v2), 2361393152 bytes
Failed to get shared "write" lock  # 被 VM 锁住，说明在使用中
```

文件是有效的 qcow2 镜像，661MB，有操作系统。

**进一步分析 QEMU 启动命令：**

在 virt-launcher 日志中发现：
```
-blockdev {"driver":"file","filename":"...cpu-node-1.qcow2",...}
-blockdev {"node-name":"libvirt-2-format","driver":"raw",...}
```

**关键问题找到：QEMU 用 `driver=raw` 读取 qcow2 文件！**

查阅 KubeVirt GitHub Issues 确认：

> **Issue #2705**: "Kubevirt does not support qcow2 when loading a hostDisk (always shows in qemu as format=raw)"

**这就是所有问题的根源：** KubeVirt 的 `hostDisk` 类型始终以 raw 格式读取磁盘文件，无法识别 qcow2 格式。qcow2 文件被当 raw 读，bootloader 数据完全错误，VM 无法引导，所以：
- 串口没有任何输出（系统没起来）
- 网络不通（cloud-init 没跑）
- guest agent 不存在

---

### 阶段六：grub 串口配置问题（并行排查）

在发现镜像格式问题之前，同时排查了 grub 配置问题。

**操作：** 用 nbd 挂载镜像检查 grub.cfg

```bash
sudo modprobe nbd max_part=8
sudo qemu-nbd --connect=/dev/nbd0 /opt/k8s-workspace/images/cpu-node-1.qcow2
sudo mount /dev/nbd0p1 /mnt
grep "ttyS0\|terminal\|serial" /mnt/boot/grub/grub.cfg
```

**发现：**
```
terminal_input console    # 只输出到 VGA，没有 serial
terminal_output console
linux ... console=tty1 console=ttyS0   # 内核参数有 ttyS0，但 grub 本身不输出到串口
```

**操作：** 修改 grub.cfg

```bash
sudo sed -i 's/terminal_input console/terminal_input serial console/' /mnt/boot/grub/grub.cfg
sudo sed -i 's/terminal_output console/terminal_output serial console/' /mnt/boot/grub/grub.cfg
```

**结果：** 串口日志依然为空，因为镜像格式问题才是根本原因，grub 改动无效（系统根本没启动）。

---

### 阶段七：CirrOS 测试验证 console 机制

为了排除 KubeVirt console 机制本身的问题，用官方 containerDisk 镜像测试：

```yaml
volumes:
  - name: sys-disk
    containerDisk:
      image: quay.io/kubevirt/cirros-container-disk-demo:latest

**结果：**

```

**结论：** `virtctl console` 机制本身完全正常，问题100%在 Ubuntu 镜像这侧。

## 四、解决方案

### 4.1 制作 Ubuntu 模板镜像

**下载官方 cloud image：**
```bash
wget https://cloud-images.ubuntu.com/jammy/current/jammy-server-cloudimg-amd64.img \
  -O /opt/k8s-workspace/images/ubuntu-base.img

# 扩容到 20G（原始只有约 2.2G）
qemu-img resize /opt/k8s-workspace/images/ubuntu-base.img 20G
```

**挂载镜像进行预配置：**
```bash
sudo modprobe nbd max_part=8
sudo qemu-nbd --connect=/dev/nbd0 /opt/k8s-workspace/images/ubuntu-base.img
sudo mount /dev/nbd0p1 /mnt
sudo mount --bind /dev /mnt/dev
sudo mount --bind /proc /mnt/proc
sudo mount --bind /sys /mnt/sys
sudo cp /etc/resolv.conf /mnt/etc/resolv.conf
```

**创建配置脚本（解决 chroot 内 sudo pty 问题）：**
```bash
sudo tee /mnt/setup.sh <<'EOF'
#!/bin/bash
export http_proxy=http://192.168.1.72:7897
export https_proxy=http://192.168.1.72:7897

# 开启串口输出
sed -i 's/GRUB_CMDLINE_LINUX_DEFAULT=.*/GRUB_CMDLINE_LINUX_DEFAULT="console=tty0 console=ttyS0,115200n8"/' /etc/default/grub
echo 'GRUB_TERMINAL="serial console"' >> /etc/default/grub
echo 'GRUB_SERIAL_COMMAND="serial --speed=115200 --unit=0 --word=8 --parity=no --stop=1"' >> /etc/default/grub
update-grub

# 开启串口 getty 服务
systemctl enable serial-getty@ttyS0.service

# 安装 qemu-guest-agent（需要代理）
apt-get update
apt-get install -y qemu-guest-agent

# 开启 SSH 允许 root 登录
sed -i 's/#PermitRootLogin.*/PermitRootLogin yes/' /etc/ssh/sshd_config

# 创建 ubuntu 用户（cloud image 默认用户）
useradd -m -s /bin/bash ubuntu 2>/dev/null || true
echo 'ubuntu:leo' | chpasswd
usermod -aG sudo ubuntu
EOF

sudo chmod +x /mnt/setup.sh
sudo chroot /mnt /bin/bash /setup.sh
```

> **注意：** chroot 内遇到 `sudo: unable to allocate pty` 错误，解决方法是将命令写入脚本文件后用 `sudo chroot /mnt /bin/bash /script.sh` 执行，避免交互式 shell。

**卸载镜像：**
```bash
sudo umount /mnt/dev /mnt/proc /mnt/sys /mnt
sudo qemu-nbd --disconnect /dev/nbd0
```

**转换为 raw 格式（关键步骤）：**
```bash
sudo qemu-img convert -f qcow2 -O raw \
  /opt/k8s-workspace/images/ubuntu-base.img \
  /opt/k8s-workspace/images/ubuntu-base.raw
```

### 4.2 为每个 VM 创建独立 raw 镜像

不能使用 qcow2 差量镜像（backing file），必须每个 VM 独立完整的 raw 文件：

```bash
cd /opt/k8s-workspace/images

sudo cp ubuntu-base.raw cpu-node-1.raw
sudo cp ubuntu-base.raw cpu-node-2.raw
sudo cp ubuntu-base.raw algo-node-1.raw
sudo cp ubuntu-base.raw data-node-1.raw
sudo cp ubuntu-base.raw data-node-2.raw
sudo cp ubuntu-base.raw gpu-node-1.raw

# 设置权限（KubeVirt 以非 root 用户读取）
sudo chmod 666 *.raw
sudo chmod 644 ubuntu-base.raw ubuntu-base.img
```

---

### 4.3 cloud-init 正确配置

**错误写法（不生效）：**
```yaml
userData: |
  #cloud-config
  users:
    - name: ubuntu
      password: leo
      chpasswd: { expire: False }
      sudo: ALL=(ALL) NOPASSWD:ALL
      shell: /bin/bash
```

原因：`users` 列表对已存在用户（ubuntu）行为不一致，且未开启 SSH 密码登录。

**正确写法（参考 StarlingX 官方文档验证）：**
```yaml
userData: |
  #cloud-config
  user: leo
  password: leo
  chpasswd: { expire: False }
  ssh_pwauth: True
  runcmd:
    - netplan apply
```

关键点：
- 顶层 `user` 字段创建新用户
- `ssh_pwauth: True` 必须加，否则 SSH 默认只允许公钥登录
- 去掉 `bootcmd` 中的 grub 修改（已在镜像中完成）

## 六、经验总结与踩坑记录

### 坑1：KubeVirt hostDisk 不支持 qcow2

**现象：** VM 启动后串口无任何输出，网络不通，guest agent 不存在。

**根本原因：** KubeVirt `hostDisk` 始终以 raw 格式读取磁盘文件，qcow2 文件结构被完全误读，系统无法引导。

**解决：** 必须将镜像转换为 raw 格式。
```bash
qemu-img convert -f qcow2 -O raw input.qcow2 output.raw
```

**参考：** [KubeVirt Issue #2705](https://github.com/kubevirt/kubevirt/issues/2705)

---

### 坑2：qcow2 差量镜像（backing file）不可用

**现象：** 用 `qemu-img create -f qcow2 -b ubuntu-base.img` 创建的差量镜像无法启动。

**原因：** hostDisk 以 raw 格式读取，差量镜像依赖 backing file 机制，两者完全不兼容。

**解决：** 每个 VM 使用从 base 复制的独立完整 raw 文件。

---

### 坑3：cloud-init users 列表对已存在用户行为不一致

**现象：** 配置了 `users` 列表后，ubuntu 用户密码未更改，登录失败。

**原因：** Ubuntu cloud image 中 ubuntu 用户已存在，cloud-init 的 `users` 列表在处理已存在用户时行为不可靠。

**解决：** 使用顶层 `user/password` 字段（适用于设置默认用户），或创建全新用户名。

---

### 坑4：SSH 默认禁用密码登录

**现象：** SSH 连接报 `Permission denied (publickey)`。

**原因：** Ubuntu cloud image 默认配置 `PasswordAuthentication no`。

**解决：** cloud-init 中加入 `ssh_pwauth: True`。

---

### 坑5：chroot 内 sudo 无法分配 PTY

**现象：** 在 nbd 挂载的镜像内执行 `sudo chroot /mnt /bin/bash` 报 `unable to allocate pty`。

**原因：** SSH 会话环境下 `/dev/pts` 挂载不完整。

**解决：** 将所有命令写入脚本文件，用 `sudo chroot /mnt /bin/bash /script.sh` 执行，避免交互式 shell。

---

### 坑6：apt lock 被 unattended-upgr 占用

**现象：** `sudo apt install` 等待锁超时。

**解决：**
```bash
sudo kill -9 <unattended-upgr-pid>
sudo rm -f /var/lib/dpkg/lock-frontend /var/lib/dpkg/lock /var/cache/apt/archives/lock
sudo dpkg --configure -a
```

---

### 坑7：cloud-init 只执行一次

**现象：** 修改 yaml 中的 userData 后重启 VM，配置不生效。

**原因：** cloud-init 在系统首次启动时执行并写入完成标记，后续启动不再重新执行。

**解决：** 每次需要重新测试 cloud-init 配置时，必须重置（重新复制）镜像文件。
