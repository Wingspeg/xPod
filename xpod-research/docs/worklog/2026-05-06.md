# 工作日志 — Volcano vGPU 调度故障排查

**日期：** 2026-05-06  
**环境：** Kubernetes v1.31.14 / Volcano v1.9.0 / KubeVirt / A10 GPU passthrough  
**问题标题：** Volcano Job 提交后 PodGroup 未自动创建，Pod 无法启动

---

## 一、问题现象

提交 Volcano Job（vcjob）后：

- `kubectl get podgroup -A` 返回空，PodGroup 未被自动创建
- Job 状态始终为 `Pending`
- `kubectl describe vcjob` 显示 `Events: <none>`
- Controller 日志有 `unknown field "spec.tasks[0].template.metadata.creationTimestamp"` 警告，但无明确报错

---

## 二、排查过程

### 2.1 确认组件名称

初始执行 `kubectl get deployment volcano-controller -n volcano-system` 报 NotFound，发现实际 deployment 名称为 `volcano-controllers`（复数）。通过 `kubectl get all -n volcano-system` 确认所有组件名称。

**发现异常：**
- `deployment.apps/volcano-admission` 副本数为 `0/0`
- `deployment.apps/volcano-scheduler` 处于 `0/1`（未就绪）
- `daemonset.apps/volcano-vgpu-device-plugin` DESIRED 为 0

### 2.2 查看 controller 日志（提高过滤精度）

```
Failed to create PodGroup for Job <default/vgpu-smoke-test>:
failed calling webhook "mutatepodgroup.volcano.sh":
dial tcp 10.100.251.25:443: connect: connection refused
```

**根因确认：** `volcano-admission` deployment 副本数为 0，webhook endpoint 无法连接，导致每次创建 PodGroup 都被 MutatingWebhook 拦截后 connection refused。

### 2.3 恢复 volcano-admission

```bash
kubectl scale deployment volcano-admission -n volcano-system --replicas=1
```

admission Pod 恢复 Running，controller 错误日志消失。

### 2.4 验证 PodGroup 是否创建

使用 `kubectl get podgroup -A` 仍返回空。排查后发现集群中存在**两个 PodGroup CRD**：

- `podgroups.scheduling.sigs.k8s.io`（scheduler-plugins）
- `podgroups.scheduling.volcano.sh`（Volcano）

`kubectl get podgroup` 默认查询的是 `scheduling.sigs.k8s.io`，需要显式指定：

```bash
kubectl get podgroups.scheduling.volcano.sh -A
```

确认 PodGroup 实际已创建，但 STATUS 为空（未进入 Inqueue）。

### 2.5 发现 gpu-node-1 NotReady

```
gpu-node-1   NotReady   worker   14d
```

`volcano-scheduler` Pod 调度在 `gpu-node-1` 上，节点 NotReady 导致 scheduler 实际失联（READY 显示 0/1）。

### 2.6 排查 VM 未启动

`kubectl get vmi -A` 显示所有 6 台 KubeVirt VM 均处于 `Pending` 状态。

`kubectl describe vmi gpu-node-1` 显示：

```
Error creating pod: failed calling webhook "mutatepod.volcano.sh":
dial tcp 10.100.251.25:443: connect: connection refused
```

**根因：鸡和蛋问题**
- VM 起不来 → 因为 volcano webhook 拦截 Pod 创建
- volcano webhook 挂了 → 因为 admission Pod 之前副本数为 0
- admission 虽然已恢复，但 TLS 握手失败（`curl -k` 返回 SSL_ERROR_SYSCALL）

### 2.7 删除阻塞 VM 启动的 webhook

检查 MutatingWebhookConfigurations，发现 `volcano-admission-service-pods-mutate` 存在。删除后 VM 仍然 Pending，继续报 `validatepod.volcano.sh` 错误。

删除 `volcano-admission-service-pods-validate` 后，VM Pod 成功创建：

```
Normal  SuccessfulCreate  virtualmachine-controller  Created virtual machine pod virt-launcher-gpu-node-1-4hz26
```

### 2.8 VM Pod 调度失败：GPU 资源不足

virt-launcher Pod Pending，原因：

```
0/7 nodes: 1 Insufficient nvidia.com/GA102GL_A10, 6 node(s) had untolerated taint unreachable
```

`nvidia.com/GA102GL_A10` 在宿主机节点上显示为 `0`。

### 2.9 排查 GPU passthrough 资源未汇报

确认 KubeVirt 配置中已正确设置：

```yaml
permittedHostDevices:
  pciHostDevices:
  - externalResourceProvider: false
    pciVendorSelector: 10de:2236
    resourceName: nvidia.com/GA102GL_A10
```

查看宿主机上的 `virt-handler` 日志：

```
failed to read driver link /sys/bus/pci/devices/0000:81:00.0/driver: no such file or directory
```

**根因：** A10（PCI 0000:81:00.0）未绑定任何驱动，virt-handler 无法识别为可用 passthrough 设备。

检查 vfio 模块：`lsmod | grep vfio` 返回空。

### 2.10 加载 vfio-pci 并绑定 A10

```bash
sudo modprobe vfio-pci
echo "10de 2236" | sudo tee /sys/bus/pci/drivers/vfio-pci/new_id
# 返回 "File exists"，设备已有 ID 记录
echo "0000:81:00.0" | sudo tee /sys/bus/pci/drivers/vfio-pci/bind
# 返回 "Device or resource busy"
```

确认 `lspci -k -s 81:00.0` 显示 `Kernel driver in use: vfio-pci`，说明设备实际已绑定，"busy" 是因为重复绑定操作。

virt-handler 日志随后出现：

```
nvidia.com/GA102GL_A10 device plugin started
```

节点资源更新：`nvidia.com/GA102GL_A10: 1`

### 2.11 文件描述符限制问题（ulimit）

宿主机 `ulimit -n` 为 **1024**，virt-handler 和 volcano-scheduler 均报：

```
failed creating filewatcher: too many open files
```

**修复方案（永久生效）：**

```bash
echo "* soft nofile 65536
* hard nofile 65536" | sudo tee -a /etc/security/limits.conf

sudo mkdir -p /etc/systemd/system/kubelet.service.d/
echo "[Service]
LimitNOFILE=65536" | sudo tee /etc/systemd/system/kubelet.service.d/limits.conf

sudo systemctl daemon-reload
sudo systemctl restart kubelet
```

验证：`cat /proc/$(pgrep kubelet)/limits | grep "open files"` → `1000000`

gpu-node-1 VM 内同步执行相同操作。

### 2.12 Webhook 配置不完整导致 admission CrashLoopBackOff

之前手动删除了 `volcano-admission-service-pods-mutate` 和 `volcano-admission-service-pods-validate`，导致 admission Pod 启动时无法注册 webhook 配置，持续 CrashLoopBackOff。

**修复：** 找到原始安装文件，重新 apply：

```bash
kubectl apply -f /opt/k8s-workspace/volcano-development.yaml
```

重新创建了以下 webhook 配置：
- `volcano-admission-service-pods-mutate`
- `volcano-admission-service-podgroups-mutate`
- `volcano-admission-service-jobs-mutate`
- `volcano-admission-service-jobs-validate`
- `volcano-admission-service-pods-validate`

`volcano-admission-init` job 完成（7s），所有 webhook TLS 证书重新签发。

### 2.13 重启 volcano-scheduler 并验证

```bash
kubectl rollout restart deployment/volcano-scheduler -n volcano-system
```

## 四、问题根因总结

| 层级 | 根因 |
|------|------|
| 直接原因 | `volcano-admission` deployment 副本数被设为 0，webhook 不可用 |
| 间接原因 | admission 不可用导致 KubeVirt VM Pod 创建失败，所有 worker 节点 NotReady |
| 底层原因 | 宿主机 `vfio-pci` 模块未加载，GPU passthrough 资源无法汇报 |
| 系统限制 | 宿主机 `ulimit -n` 仅 1024，导致 virt-handler / scheduler 文件监听器创建失败 |
| 操作失误 | 手动删除 volcano webhook 配置后未重新注册，导致 admission 无法启动 |

## 六、经验教训

1. **双 CRD 陷阱：** 集群中同时存在 `scheduling.sigs.k8s.io` 和 `scheduling.volcano.sh` 两套 PodGroup CRD，`kubectl get podgroup` 默认查询前者，容易误判为"未创建"。
2. **webhook 删除需谨慎：** 手动删除 webhook 配置会导致 admission-init 重新运行时无法恢复完整状态，应优先通过调整 `failurePolicy: Ignore` 临时规避，而非直接删除。
3. **vfio-pci 需持久化：** 模块加载和设备绑定在重启后会丢失，需写入 udev rules 和 modules-load.d 才能持久。
4. **ulimit 是基础设施前提：** 在高密度容器节点上，默认的 1024 文件描述符限制远远不够，应作为节点初始化的标准步骤。
