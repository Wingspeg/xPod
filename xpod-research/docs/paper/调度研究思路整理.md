# 算力网络调度研究：思路整理与实验设计

## 1. 研究背景与问题定义

### 理论基础

**网络计算（Network Computing）**
网络计算是指通过网络将分散的计算资源连接起来，形成统一的计算能力，用户通过网络访问和使用这些资源，而无需关心资源的物理位置。这是本研究的核心背景——算力网络时代，算力、数据、算法都分散在网络的不同节点上，以服务的形式对外暴露，需要统一调度。

**服务计算（Service Computing）**
服务计算是指将计算能力、数据、算法等资源封装为独立的、可通过网络访问的服务单元（Service），通过服务组合和编排完成复杂任务。本研究将三要素抽象为网络服务：

```
算力节点  → 算力服务（Compute Service）  通过 IP:Port 访问
数据节点  → 数据服务（Data Service）     通过 IP:Port 访问
算法节点  → 算法服务（Algorithm Service） 通过 IP:Port 访问
```

**两者的结合**
在网络计算和服务计算的思想框架下，本研究提出 xPod 作为统一的服务编排单元：

```
网络计算  → 三要素通过网络提供和访问（理论背景）
服务计算  → 三要素封装为独立服务（设计思想）
xPod     → 服务编排与统一调度单元（本文贡献）
```

### 核心问题
在算力网络时代，传统"仅调度算力"的模式已遭遇瓶颈。本研究探索**算法服务、算力服务、数据服务三要素的统一协同调度**，验证其相比单独调度算力的效能提升。

### 统一表征的切入点
以"服务调用图"为中心，三要素共同建模，网络作为底层通信基础设施体现在边的属性上：

- **算法服务** → 图的拓扑结构（服务类型、依赖关系、算子图）
- **数据服务** → 图上流动的数据流（数据位置、热度、访问代价）
- **算力服务** → 图节点的执行约束（显存、FLOPS、带宽、延迟）
- **网络**     → 图的边属性（节点间延迟、带宽、传输代价），不是独立要素，是三要素之间通信的基础设施

三者在同一张服务调用图里共存：算力服务内化为节点计算代价函数，数据服务决定边的数据传输代价（受网络约束），算法服务决定图的拓扑结构。

### 图表示方案选择

| 方案 | 特点 | 优点 | 缺点 |
|------|------|------|------|
| **DAG（有向无环图）** | 有明确依赖顺序，无环 | 拓扑清晰，编译器领域成熟，实现简单，工程落地容易 | 无环限制较强，服务调用若有循环依赖需额外处理 |
| **异构图（Heterogeneous Graph）** | 节点/边均有多种类型 | 天然支持三要素（算力/数据/算法），边可带网络代价属性，GNN可直接用于调度决策，技术含量高 | 实现复杂度较高，工程落地难 |
| **超图（Hypergraph）** | 一条边可连接多个节点 | 适合描述"一个任务同时依赖多个服务"的场景 | 不够直观，优化难度大 |
| **知识图谱（Knowledge Graph）** | 实体+关系建模 | 适合做推理和查询 | 不适合做调度优化，偏离工程落地 |

本研究实现与实验评测阶段采用 **DAG** 作为统一表征：把算法/数据/算力抽象为 DAG 的节点与属性，把网络与数据搬运代价体现在边的属性与代价函数中，优先保证实现可落地、实验可复现。

## 2. 核心创新：xPod 抽象

### 问题
k8s 原生 Pod 是单层抽象，只描述计算容器本身，无法感知服务计算中的三要素：

```yaml
# 原生 k8s Pod（单层）
spec:
  containers:
  - image: training:latest
    resources:
      requests:
        cpu: "4"
        memory: "8Gi"
  # 只知道"跑什么容器"
  # 不知道"需要哪个算力服务"、"依赖哪个数据服务"、"调用哪个算法服务"
```

### xPod 定义
xPod 是本研究提出的新资源抽象，在**网络计算和服务计算**思想下，将 k8s Pod 扩展为**三要素统一描述的服务编排单元**：

```
xPod = 算力服务需求 + 数据服务需求 + 算法服务描述
```

```yaml
# xPod（三层服务编排单元）
apiVersion: scheduling.xcloud.io/v1
kind: XPod
metadata:
  name: training-job
spec:
  # 算力服务层（Compute Service）
  compute:
    type: GPU              # GPU / CPU
    memory: 20Gi           # 显存需求
    flops: 125T            # 算力需求（TFLOPS）
    topology: NVLink       # 拓扑要求（是否需要NVLink互联）
    scheduler: volcano     # 路由到 Volcano 算力服务调度器

  # 数据服务层（Data Service）
  data:
    dataset: cluster-trace # 数据集名称
    location: data-node-1  # 数据服务所在节点（IP可达）
    size: 10Gi             # 数据大小
    scheduler: fluid       # 路由到 Fluid 数据服务调度器

  # 算法服务层（Algorithm Service）
  algorithm:
    image: resnet50:latest    # 算法服务镜像（从 algo-node 拉取）
    framework: pytorch        # 框架
    type: CNN                 # 模型类型
    batch_size: 64            # 超参数
    learning_rate: 0.001      # 超参数
    scheduler: koord-scheduler # 路由到 Koordinator 算法服务调度器
```

### xPod 服务编排流程

```
用户提交 xPod（描述三要素服务需求）
      ↓
xPod Controller 解析三层服务需求
      ↓
算力服务层  → 生成 Volcano Job    → 调度到算力服务节点（gpu-node）
数据服务层  → 生成 Fluid Dataset  → 数据服务预热缓存到计算节点
算法服务层  → 生成训练 Job        → 调度到算法服务节点（algo-node）执行
      ↓
三层服务协同运行，完成完整计算任务
```

### 三要素服务对称性

三者逻辑完全统一，都是**网络可访问的服务**，都有"服务位置"，都需要"服务感知调度"：

```
数据服务   → 部署在 data-node，通过 Fluid 感知位置，预热缓存到计算节点
算力服务   → 部署在 gpu/cpu-node，通过 Volcano/Koordinator 调度
算法服务   → 部署在 algo-node，通过 xPod 描述，调度到合适服务节点执行
```

### 与原生 Pod 的对比

| 维度 | k8s Pod | xPod |
|------|---------|------|
| 抽象层次 | 单层（计算容器） | 三层（算力服务+数据服务+算法服务） |
| 设计思想 | 容器编排 | 服务计算 + 网络计算 |
| 调度感知 | 只感知 CPU/内存 | 感知算力拓扑、数据服务位置、算法服务类型 |
| 调度器 | 单一（default-scheduler） | 多服务调度器协同（Volcano/Fluid/Koordinator） |
| 数据感知 | 无 | 感知数据服务位置，提前预热 |
| 表达能力 | 只能说"跑什么容器" | 能说"调用哪些服务+服务在哪+怎么协同" |

## 3. 系统架构

### 整体架构（服务计算视角）

```
用户提交 xPod
      ↓
┌─────────────────────────────────────┐
│         服务感知层（统一表征）          │
│  解析三要素服务需求，构建服务调用图      │
└─────────────────────────────────────┘
      ↓
┌─────────────────────────────────────┐
│         服务路由层（任务分类）          │
│  识别服务类型，路由到对应服务调度器      │
└─────────────────────────────────────┘
      ↓
┌──────────────┬──────────────┬────────────────┐
│  算力服务层   │  数据服务层   │   算法服务层    │
│   Volcano   │    Fluid     │  Koordinator   │
│ gpu/cpu-node│  data-node   │   algo-node    │
└──────────────┴──────────────┴────────────────┘
```

### 服务组件选型

| 组件 | 服务职责 | 选型理由 |
|------|---------|---------|
| **Volcano** | 算力服务调度 | 华为开源，Gang Scheduling，AI训练场景标准方案 |
| **Fluid** | 数据服务编排 ✓ | 与 Volcano 原生集成，数据服务位置感知，部署简单（已确认，替代 Alluxio）|
| **Koordinator** | 算法服务调度 | 阿里开源，CPU绑核、NUMA感知、QoS分级，生产级验证 |

### 多服务调度器共存方案
三个服务调度器通过 `schedulerName` 字段区分，互不干扰：

```yaml
# 算力服务任务
schedulerName: volcano

# 算法服务任务
schedulerName: koord-scheduler

# 数据服务任务（通过 Fluid Dataset CRD 管理）
```

## 4. 调度机制

### 调度目标
在满足三要素服务需求的前提下，最小化任务端到端完成时间：

$$\min \; T_{total} = T_{compute} + T_{data} + T_{network}$$

其中：
- $T_{compute}$：算力服务执行时间
- $T_{data}$：数据服务传输时间
- $T_{network}$：服务间网络通信时间

### 缓存感知调度

调度器在决策时感知数据服务的缓存状态，优先将任务调度到数据已缓存的节点：

```
第一次调度（冷启动）：
  数据在 data-node → 跨节点搬运到计算节点 → Fluid 缓存到本地 → 执行
  T_data 较大

第二次调度（缓存命中）：
  数据已在计算节点本地缓存 → 直接读取 → 执行
  T_data ≈ 0，JCT 显著降低
```

缓存命中率作为新指标加入代价函数：

$$C = \alpha \cdot T_{compute} + \beta \cdot T_{data} \cdot (1 - \text{hit\_rate}) + \gamma \cdot T_{network}$$

缓存命中率越高，数据传输代价越低，调度器优先选择命中缓存的节点组合。

### 两阶段调度算法

**第一阶段：服务感知过滤（Filtering）**

收到 xPod 后，根据三要素服务需求过滤不满足条件的节点：

```
算力服务过滤：
  → 节点显存 ≥ xPod.compute.memory
  → 节点 FLOPS ≥ xPod.compute.flops
  → 节点拓扑满足 xPod.compute.topology

数据服务过滤：
  → 数据服务节点网络可达
  → 网络延迟 ≤ 阈值
  → 优先选择数据已缓存的节点（缓存命中优先）

算法服务过滤：
  → 节点 CPU/内存满足算法服务需求
  → 节点 QoS 等级满足要求
```

**第二阶段：代价函数优化（Scoring）**

在满足条件的候选节点中，计算综合代价，选代价最小的执行：

$$C = \alpha \cdot T_{compute} + \beta \cdot T_{data} \cdot (1 - \text{hit\_rate}) + \gamma \cdot T_{network}$$

| 参数 | 含义 | 默认权重 |
|------|------|---------|
| $\alpha$ | 算力服务代价权重 | 0.5 |
| $\beta$ | 数据服务传输代价权重 | 0.3 |
| $\gamma$ | 网络通信代价权重 | 0.2 |
| $\text{hit\_rate}$ | 数据缓存命中率 | 运行时动态计算 |

权重可根据任务类型动态调整（GPU密集型任务加大 $\alpha$，数据密集型任务加大 $\beta$）。

### 与现有调度器的关系

xPod 的两阶段调度是**上层编排决策**，Volcano/Fluid/Koordinator 是**下层执行调度**，两者分工明确：

```
xPod 调度层（上层）：决定"哪类服务去哪个节点"，感知缓存状态
      ↓
Volcano / Fluid / Koordinator（下层）：决定"具体怎么分配资源"
Fluid 负责缓存管理，将热点数据预热到计算节点本地
```

## 5. 模拟集群方案

### 设计思路
用单台物理机开 KVM 虚拟机，每个 VM 分配独立 IP，作为 k8s worker node 加入集群。每个节点对外暴露一类服务，通过网络 IP 访问，模拟"来自五湖四海的服务器通过网络汇聚"的算力网络场景。

```
gpu-node  → 对外暴露算力服务（Compute Service，真实 GPU）
cpu-node  → 对外暴露算力服务（Compute Service，CPU）
data-node → 对外暴露数据服务（Data Service）
algo-node → 对外暴露算法服务（Algorithm Service）
```

- 每个服务节点有真实 IP，真实网络通信
- 节点间跨网络服务调用，数据服务感知优势更明显
- 三类服务节点通过 IP 挂载访问，体现网络计算思想

### VM 规划（6个服务节点）

| VM | IP | 节点名 | 服务类型 | 规格 | 备注 |
|----|-----|--------|---------|------|------|
| VM1 | 192.168.1.121 | gpu-node-1 | 算力服务节点（GPU） | 8核 32G 100G | PCIe Passthrough A10 24G + vGPU Device Plugin |
| VM2 | 192.168.1.131 | cpu-node-1 | 算力服务节点（CPU） | 4核 8G 40G | |
| VM3 | 192.168.1.132 | cpu-node-2 | 算力服务节点（CPU） | 4核 8G 40G | |
| VM4 | 192.168.1.141 | data-node-1 | 数据服务节点 | 4核 8G 40G | |
| VM5 | 192.168.1.142 | data-node-2 | 数据服务节点 | 4核 8G 40G | |
| VM6 | 192.168.1.151 | algo-node-1 | 算法服务节点 | 4核 8G 40G | |

> **GPU 节点说明**：物理机仅有 1 张 NVIDIA A10（24G），通过 PCIe Passthrough 透传给 gpu-node-1，并在该节点部署 vGPU Device Plugin 做显存虚拟化（最多支持多 Pod 共享显存）。由于 HAMi 与 Volcano（gang scheduling）存在冲突，这里以 vGPU Device Plugin 替代。实验的调度逻辑验证不依赖多张物理 GPU，单 GPU 节点足以触发 Volcano GPU 调度路径并采集真实 JCT 指标。

### 资源消耗

```
物理机总量：72核  251G  1.8T
VM 消耗：   28核   72G  300G
剩余：      44核  179G  1.5T  → 宿主机开销 + 实验余量
```

### 服务路由

```
xPod 提交
  ↓ 解析服务需求类型
  ↓
算力服务请求（GPU） → Volcano      → 路由到算力服务节点 gpu-node-1
算力服务请求（CPU） → Volcano      → 路由到算力服务节点 cpu-node-1/2
算法服务请求        → Koordinator  → 路由到算法服务节点 algo-node-1
数据服务请求        → Fluid        → 路由到数据服务节点 data-node-1/2
```

## 6. 实验数据方案（半合成半真实）

### 设计原则
- 全真实数据：服务器资源不够，下载和存储压力大
- 全合成数据：缺乏说服力
- **半合成半真实**：真实数据保证可信度，合成数据扩展规模

### 数据集：Alibaba Cluster Trace GPU v2020

| 属性 | 详情 |
|------|------|
| **来源** | 阿里巴巴生产 GPU 集群真实负载 |
| **开源地址** | github.com/alibaba/clusterdata |
| **版本** | cluster-trace-gpu-v2020 |
| **内容** | 真实 GPU 任务、CPU 任务、数据读写记录 |
| **字段** | 任务到达时间、资源请求量、执行时长、任务类型 |
| **规模** | 数千个真实任务，覆盖数天的集群负载 |

**选用理由：**
- 来自阿里巴巴生产集群，真实性强，审稿人认可度高
- 天然包含三要素服务：算力请求（GPU/CPU）、数据访问记录、算法任务类型
- 可直接用任务到达时间戳做**服务负载回放**，模拟真实算力网络服务调用场景
- 与本研究主题（算力网络服务调度）高度契合

**使用方式：**
```
从 trace 中回放真实服务请求
  ↓
按原始时间戳模拟服务请求陆续提交到算力网络
  ↓
对照组（原生 k8s，无服务感知）处理这批请求
  vs
本方案（xPod + 三服务调度器）处理同一批请求
  ↓
对比 JCT、服务利用率、服务等待时间
```

### 各场景数据来源

| 场景 | 数据类型 | 具体方案 | 数据量 |
|------|---------|---------|--------|
| **场景一**：算法服务调度 | 真实 trace + 合成 | 从 trace 提取 CPU 任务回放 + 合成 CSV 补充 | 1–5G |
| **场景二**：数据服务加载 | 真实 trace + 合成扩展 | trace 数据访问记录（真实）+ dd 扩展大文件（合成） | 10–20G |
| **场景三**：算力服务调度 | 真实 trace | 从 trace 提取 GPU 任务回放 | 按 trace 原始规模 |
| **场景四**：三服务联合 | 混合 | 完整 trace 回放，端到端服务 pipeline | ~25G |

## 8. 实验设计

### 对照组策略

本研究以"原生 k8s（default-scheduler，无服务感知）"作为统一对照组，验证本方案在四个场景下的收益，并补充必要的消融（如禁用 Fluid 缓存、禁用 QoS 分级等）以定位收益来源。

### 对比矩阵

| 场景 | 对照组 | 本方案 | 对比指标 |
|------|--------|--------|---------|
| **场景一**：算法服务调度 | 原生 k8s（无 QoS/服务感知） | Koordinator（服务 QoS 感知） | 平均JCT、P99 JCT、队列等待时间 |
| **场景二**：数据服务加载 | 原生 k8s（无数据位置/缓存感知） | Volcano + Fluid（数据服务感知与缓存） | 数据加载时间、缓存命中率、I/O wait、JCT |
| **场景三**：算力服务调度 | 原生 k8s（无 Gang/拓扑约束） | Volcano（Gang/拓扑约束调度） | GPU 利用率、平均JCT、Makespan |
| **场景四**：三服务联合 | 原生 k8s（无三要素协同） | xPod + Volcano + Fluid + Koordinator | 端到端 JCT、Makespan、资源利用率 |

### 各场景设计说明

**场景一（算法服务调度）**
- 高并发 CPU 任务提交，验证服务 QoS 感知调度的优势

**场景二（数据服务加载）**
- 数据部署在远端节点，验证数据服务位置感知和缓存加速的效果
- 额外对比冷启动（无缓存）vs 热启动（缓存命中）的 JCT 差距

**场景三（算力服务调度）**
- 高并发 GPU 任务提交（回放 trace，sleep Pod 模拟执行），验证 Gang Scheduling 的优势
- gpu-node-1 为唯一 GPU 节点，vGPU Device Plugin 管理显存隔离，多 Pod 并发调度至同一节点

**场景四（三服务联合）**
- 完整端到端 pipeline，三要素服务协同运行

## 9. 指标设计

### 领域标准指标

参考调度系统领域常见评测惯例，标准指标体系如下：

| 指标 | 含义 |
|------|------|
| **平均 JCT（Avg. JCT）** | 所有任务平均完成时间（核心指标） |
| **Makespan** | 所有任务全部完成的总时间 |
| **尾部 JCT（P95/P99）** | 最慢那批任务的完成时间，体现稳定性 |
| **队列等待时间** | 任务从提交到开始执行的时间 |
| **GPU 资源利用率（GRU）** | GPU 实际使用时间占总时间的比例 |
| **Goodput** | 吞吐量 × 统计训练效率（偏训练场景，非必须） |

### 本研究采用的指标

结合领域标准和本研究场景，采用以下四个指标：

| 指标 | 对应场景 |
|------|---------|
| **平均 JCT** | 全部四个场景 |
| **Makespan** | 场景四（三服务联合） |
| **P99 JCT** | 场景一（CPU服务稳定性） |
| **资源利用率** | 场景三（GPU算力服务） |
| **缓存命中率** | 场景二（数据服务加载） |
| **冷/热启动 JCT 对比** | 场景二 |

> Goodput 不采用：实现复杂，且本研究重心在三要素服务协同调度效果，不在单一训练任务的统计效率。
